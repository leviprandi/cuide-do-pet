# Diário Técnico do Projeto - Cuide do Pet

## Objetivo do diário

Registrar, de forma cronológica, objetiva e rastreável, os fatos reais do projeto (o que foi executado, decidido, problemas encontrados e estado atual), sem inventar etapas e sem mascarar falhas.

## Contexto atual do projeto

- **Produto:** Cuide do Pet
- **Estratégia atual:** desenvolvimento local-first, baixo custo inicial, sem deploy na primeira fase
- **Stack definida:**
  - Frontend: Next.js + TypeScript
  - Backend: NestJS
  - Banco: PostgreSQL local
  - ORM: Prisma
  - Provedor de IA: MiniMax
- **Objetivo do MVP:** registrar rotina do pet, organizar histórico, controlar gastos e usar IA para transformar linguagem natural em registros úteis

## Decisões tomadas

1. **Abordagem incremental:** O MVP será construído com mudanças pequenas e validáveis a cada etapa.
2. **Escopo rigoroso:** Não expandir escopo fora do fluxo prioritário inicial (healthcheck, pets, events, expenses, IA mínima).
3. **Qualidade de erro:** Regra obrigatória: nunca usar fallback que esconda erro real.
4. **Separação de responsabilidade:** Backend valida regras críticas; IA interpreta, mas não decide sozinha campos críticos.
5. **Fail-fast:** Configurações obrigatórias devem falhar cedo quando ausentes.
6. **Governança de projeto:** AGENTS na raiz é o ponto de verdade para diretrizes do agente.
7. **Provedor de IA:** MiniMax definido como provedor para reduzir custo.
8. **Execução prática por padrão:** para pedidos acionáveis, executar por edição direta no repositório, com mudanças mínimas, rastreáveis e sem inventar progresso.
9. **Seleção de skill:** consultar primeiro `skills/SKILLS_QUICK_REFERENCE.md`; usar o catálogo completo apenas quando necessário.

## Problemas encontrados

### 1. Conflito de `.gitkeep` em `apps/web` durante inicialização do Next.js
- **Problema:** `.gitkeep` estava presente em `apps/web` quando `create-next-app` foi executado, causando conflito de inicialização.
- **Impacto:** Frontend não compilava corretamente.
- **Resolução:** `.gitkeep` foi removido.
- **Status:** ✓ Resolvido

### 2. Revalidação de estrutura do monorepo (2026-03-26)
- **Problema:** Documento central registrou ausência da árvore esperada no root, sinalizando inconsistência ou falha de validação anterior.
- **Impacto:** Bloqueio momentâneo de confirmação de Fase 1.
- **Resolução:** Estrutura foi validada como presente no workspace atual.
- **Status:** ✓ Resolvido (mas validação documental ainda pendente)

### 3. Inconsistência de provedor de IA entre documentos
- **Problema:** `docs/EXECUCAO_MVP.md` cita OpenAI API, enquanto AGENTS principal define MiniMax.
- **Impacto:** Risco de implementação divergente na fase de IA.
- **Status:** ✓ Resolvido 

### 4. Prisma schema ainda não configurado em `apps/api`
- **Problema:** Prisma estava sem schema inicial e sem migrations em `apps/api`.
- **Impacto:** Bloqueava validação de banco de dados e andamento real de entidades do MVP.
- **Resolução:** Schema inicial mínimo (`User` e `Pet`) foi definido em `apps/api/prisma/schema.prisma`.
- **Status:** ✓ Resolvido

### 5. Bloqueio de conexão local com PostgreSQL (`P1001`)
- **Problema:** Prisma não consegue alcançar `localhost:5432`.
- **Impacto:** impede `prisma migrate dev`.
- **Evidência técnica:** checagem local não encontrou serviço PostgreSQL e a porta `5432` não está ouvindo.
- **Resolução:** PostgreSQL operacionalizado via Docker (`docker compose up -d`), com container `cuide-do-pet-db` em execução e migrations aplicadas com sucesso.
- **Status:** ✓ Resolvido

### 6. Ausência de `PrismaService` em `apps/api/src`
- **Problema:** não existe `PrismaService` no backend para injeção no `PetsService`.
- **Impacto:** impede implementação do módulo `pets` conforme requisito de reutilizar `PrismaService` existente (sem criar novo).
- **Evidência técnica:** busca por `PrismaService` em `apps/api/src/**/*.ts` sem ocorrências.
- **Resolução:** `PrismaService` criado e exportado por `PrismaModule`, com import no `AppModule`.
- **Status:** ✓ Resolvido

### 7. `User.updatedAt` inconsistente (`1970-01-01...`)
- **Problema:** foi observado um valor de `User.updatedAt` como `1970-01-01...`.
- **Impacto:** indica possível inconsistência de dados de timestamp e requer revisão técnica posterior.
- **Status:** ⏳ Em aberto — acompanhamento técnico não bloqueante para o MVP atual

### 8. Banco local sem `User` inicial para fluxos do frontend
- **Problema:** na sessão local atual, a tabela `User` estava vazia; `POST /pets` e `POST /expenses` exigem `userId` existente, mas o frontend atual não provê criação nem seleção de usuário.
- **Impacto:** a primeira tentativa real de criação de Pet pelo frontend falhou com HTTP 404, bloqueando a validação E2E completa sem massa manual.
- **Evidência técnica:** `select id, email, "createdAt" from "User" order by "createdAt" asc;` retornou 0 linhas e a UI exibiu `API request failed (/pets) - HTTP 404: {"message":"User with id '11111111-1111-4111-8111-111111111111' not found","error":"Not Found","statusCode":404}`.
- **Resolução:** mantida a massa já inserida na sessão anterior e criado o script manual `seed-local-qa-user.command` para provisionar de forma explícita, idempotente e rastreável o mesmo `User` local de QA em novos ambientes sem depender de `INSERT` manual.
- **Status:** ✓ Resolvido
